# Craft method

Use the relevant domain playbook as a working reference, not as a substitute for
the user's brief or the project's established requirements. Its defaults are
overridable. Existing instruction hierarchy, tool constraints, and permissions
still apply. A playbook never authorizes sending, publishing, deployment,
fabrication, paid generation, or extra agents on its own.

## The compact contract

Before substantial work, write down the audience or consumer, intended effect,
deliverable, constraints, existing assets, and observable acceptance evidence.
Keep it to one page. Separate fixed requirements from reversible assumptions.
For a small edit, these can be a few working notes; do not create a planning
ceremony. Ask only about missing decisions that materially change the result.

Load the relevant source and the smallest context that supports the task.
Keep canon, requirements, references, and decisions in the project that owns them.
Prefer a brief under 400 words and a working reference under 2,000 words; these
are attention budgets, not reasons to omit a critical contract or source.
Keep at most 20 general lessons, replacing weaker ones. Specific rulings belong
in the project ledger. Never turn every past defect into a universal rule.

## Prove the difficult part early

Make a representative pilot that exposes the highest uncertainty: a vertical
code path, a verse and chorus, a thumbnail composition, or a model blockout and
critical fit. Pick it for what could fail, not what is easiest to impress with.
If it fails the brief, revise the design before multiplying the work.

## Critic and revision loop

Review the actual artifact using the domain's critic lenses. Separate maker and
critic passes; independent reviewers are useful when authorized and available.
When one agent performs both passes, label the report **self-review in critic
role**. Never claim fresh judges, listening, rendering, execution, or user approval
without having that evidence. A description of an image is not an inspected image.

Each report records:

1. Artifact revision and material actually inspected; tests or views unavailable.
2. The main structural limitation: what currently limits the result's usefulness
   or impact? Cite a line, behavior, region, dimension, or reproducible scenario.
3. Up to three prioritized findings: location, consequence, proposed correction,
   and a check that would demonstrate resolution. Include more if needed to avoid
   hiding a serious defect. Prefer a cut or simplification when it helps; never
   require cuts that remove necessary behavior or expression.
4. Up to three strengths to preserve; these are not exemptions from correctness.
5. Decisions on each finding: fixed with evidence, rejected with reason, or open.

A **substantial finding** changes the brief's outcome, core structure, correctness,
usability, singability, composition, physical fit, or ability to deliver the asset.
A stylistic preference without a demonstrated consequence is optional feedback.
Fix the highest-impact cause first, then recheck affected work and regressions.
Do not mistake more detail, fewer words, or a higher self-assigned score for progress.

Repeat until a full fresh pass over the revised artifact finds no substantial
unresolved issue. This is a scoped review conclusion, not a guarantee of excellence.
If two rounds repeat the same issue without progress, change the approach or
identify the missing evidence/decision. Never auto-pass because a round limit was
reached. If resources end, report **incomplete**, with the open issues.
Optional ratings need explicit anchors and never average away a blocking defect.

## Finish with evidence

Inspect the final export or behavior in its intended use, not only the source.
Keep editable masters, source provenance, version, decisions, and validation
results. Distinguish draft, reviewed, tested, exported, installed, published, and
human-approved. Report only the stages actually completed.

